# Ticket batch automation

The premise needs one correction: launchable runs do **not** come from `templates/`. `/mypi-multi-agent` resolves exactly one `session.yaml` under configured `taskDirs`; this repo's config lists only `mypi-tasks`. `templates/` are starter manifests copied into `taskDirs[0]`, not direct run targets (`mypi-multi-agent.yaml:1-4`, `src/pi/session-path.ts:1-10`, `src/pi/session-path.ts:39-64`, `src/pi/extension.ts:97-111`).

The design that came out of this review (and supersedes its open questions) is `batch-design.md`.

## 1. What exists today, mechanically

- **F1 — One run = one task directory + one manifest + one artifact root.** `SessionConfig` is one strict object with one `ask` and one `definition_of_done[]`; `Runtime` is constructed with one `askDir`, derives one `runDetailsDir = join(askDir, "run-details")`, and writes that run there (`src/contracts/session-schema.ts:112-119`, `src/runtime/runtime.ts:261-269`, `src/runtime/runtime.ts:323-337`). This confirms prior F11's core constraint.
- **F2 — The run launcher already assumes a named single task.** `just prep <name>` requires `<taskDirs[0]>/<name>/session.yaml`, copies it into a worktree, and `just task <name>` runs `pi "/mypi-multi-agent <name>"`; the extension resolves that one name through `taskDirs`, parses the manifest, and starts one `Runtime` (`justfile:98-113`, `justfile:115-132`, `src/pi/extension.ts:143-223`, `src/pi/extension.ts:231-252`, `src/pi/extension.ts:384-412`).
- **F3 — The DoD is stored in the manifest and validated against that exact manifest.** `session.attester` is required and must name a configured agent; `FinalizeGate` drops non-attester verdicts; `criteriaSatisfied()` requires exactly one verdict per manifest criterion, in order, each `pass`, after cosmetic normalization only (`src/contracts/session-schema.ts:106-108`, `src/contracts/session-schema.ts:173-179`, `src/runtime/finalize-gate.ts:71-90`, `src/supervisor/finalization.ts:78-121`, `src/supervisor/finalization.ts:142-160`). This confirms prior F4.
- **F4 — A run terminates only through finalize/abort, and finalize tears the run down.** The supervisor prompt says `finalize` is the only finalization path; the tool calls `runtime.finalize()`, then `runtime.stop()`, `runtime.cleanup()`, and clears the active runtime (`src/pi/supervisor-prompt.md:19-24`, `src/pi/extension.ts:283-304`, `src/runtime/runtime.ts:805-818`).
- **F5 — The supervisor's extension surface is 11 orchestration tools, not 10.** The extension registers `list_agents`, `peer_status`, `dispatch_work_order`, `collect_reports`, `send_prompt`, `await_response`, `finalize`, `stop_all`, `stop`, `kill_all`, and `restart_agent` (`src/pi/extension.ts:415-651`). The prompt names the same orchestration surface and no tracker tool (`src/pi/supervisor-prompt.md:10-24`). This **contradicts prior F3's tool count**: `peer_status` makes it 11, not 10.
- **F6 — "One ask" is enforced in three places.** The schema has one `ask`; the supervisor briefing injects one `ASK:` title/description plus one DoD list; session resolution returns one `session.yaml`, not a batch (`src/contracts/session-schema.ts:129-137`, `src/pi/extension.ts:875-897`, `src/pi/session-path.ts:39-64`).
- **F7 — There is no in-repo tracker seam today.** The extension tool list has no issue/ticket operations, the supervisor prompt has none, and the runnable entry points in `package.json` and `justfile` likewise expose no ticket intake/writeback flow (`src/pi/extension.ts:415-651`, `src/pi/supervisor-prompt.md:10-24`, `package.json:6-17`, `justfile:1-139`). This confirms prior F1/F3.

## 2. The gap list

- **F8 — Missing intake/writeback layer.** Nothing in `src/` models an issue id, ticket body, ticket state, or tracker writeback; the only task lookup is `<taskDirs>/<name>/session.yaml` (`src/pi/session-path.ts:39-64`, `src/contracts/session-schema.ts:129-137`). This must live either in a new tracker adapter (`src/tracker/*` or similar) or in an external driver. Hard part: there is no current authority rule for ticket body vs comment vs generated manifest. Confirms prior F13.
- **F9 — Missing triage runner.** The measured triage loop is still text: the brief says no script, recipe, supervisor, or peer runs it, and the repo's launch/runtime seams name no triage entry point (`docs/explorations/triage-automation/triage-loop-brief.md:63-80`, `src/pi/extension.ts:384-412`, `package.json:6-17`, `justfile:1-139`). Hard part: the runner must isolate the repo, execute author + verifier, sample claim rows, and emit accept/refuse state before implementation. Confirms prior F1.
- **F10 — Missing per-ticket manifest materialization.** Execution consumes a concrete `session.yaml` under `taskDirs`; the gate compares verdicts to that manifest's DoD array; one shared batch config cannot satisfy different ticket DoDs (`src/pi/session-path.ts:39-64`, `src/contracts/session-schema.ts:112-119`, `src/supervisor/finalization.ts:96-121`). Hard part: criterion text must survive ticket/report/manifest/attester transport unchanged enough for the gate. Confirms prior F11.
- **F11 — Missing machine gate for "verified DoD accepted".** The verifier docs define "one mismatch means the DoD is not accepted," but current gate terms are for one implementation run: `dod`, `criteria`, `stale-attestation`, `validation`, `run-contract` (`docs/explorations/triage-automation/triage-verifier.md:74-95`, `src/supervisor/finalization.ts:124-160`). Hard part: batch automation needs a pre-run accept/reject checkpoint that current finalize code does not model. Confirms prior F12.
- **F12 — Missing batch controller.** The extension allows one active runtime at a time, and each runtime owns one `askDir`, one `runDetailsDir`, one `final.md`, and one `findings.md` (`src/pi/extension.ts:396-399`, `src/runtime/runtime.ts:255-269`, `src/artifacts/final-writer.ts:18-38`). Hard part: batch state, resume, and partial failure must live above ordinary runs or force a large runtime rewrite. This is the main new constraint beyond prior F1-F13.
- **F13 — Missing enforceable model-family separation.** The triage verifier requires a different model family from the author, but the manifest schema stores raw `model` strings only and has no family/group field (`docs/explorations/triage-automation/triage-verifier.md:74-82`, `src/contracts/session-schema.ts:11-24`, `src/contracts/session-schema.ts:129-137`). Hard part: a fully automatic batch cannot verify this invariant without new catalog or schema data. Confirms prior F12.

## 3. Candidate architectures

- **O1 — External driver loop (shell/script/justfile).** Reuse `mypi-multi-agent.yaml`, `just task <name>`, and the existing run lifecycle; add a driver that selects tickets, runs triage + verifier, renders one manifest per accepted ticket into `taskDirs[0]`, then launches ordinary runs serially (`mypi-multi-agent.yaml:1-4`, `justfile:98-132`, `src/pi/session-path.ts:39-64`). It cannot make triage acceptance part of today's finalize gate because triage happens before a run exists. If ticket 3/8 is unworkable, the driver can emit a refusal artifact and either continue or stop by policy.
- **O2 — New extension-level batch command.** Add a new top-level command beside `/mypi-multi-agent` that owns tracker intake, triage/verifier, manifest generation, and sequential ordinary run launches via `loadSession()` / `startRun()`-like seams (`src/pi/extension.ts:143-223`, `src/pi/extension.ts:231-252`, `src/pi/extension.ts:384-412`). It **cannot** be "the current supervisor starts more runs" without new tooling: the in-run supervisor has no launch tool, and `/mypi-multi-agent` refuses while a runtime is active (`src/pi/supervisor-prompt.md:10-24`, `src/pi/extension.ts:396-399`). If ticket 3/8 is unworkable, this command can refuse it before spawning run 3 and continue/stop by policy.
- **O3 — Batch inside one runtime.** Add a new batch schema/run type whose supervisor first triages tickets, then dispatches implementation work inside the same runtime. Existing seams are `SessionConfig`, `Runtime`, `FinalizeGate`, `FinalWriter`, and peer assembly (`src/contracts/session-schema.ts:129-137`, `src/runtime/runtime.ts:261-338`, `src/runtime/finalize-gate.ts:56-90`, `src/artifacts/final-writer.ts:18-38`, `src/peer/peer-main.ts:180-203`). It structurally cannot preserve today's finalize semantics unchanged, because one runtime has one ask, one DoD array, and one terminal artifact pair. If ticket 3/8 is unworkable, either the whole batch run fails, or you invent new partial-success semantics and sub-artifact layout.

## 4. Invariants any design must preserve

- **F14 — One executable task still needs one manifest.** `resolveSessionPath()` returns one manifest, `buildBriefing()` injects one DoD list, and `criteriaSatisfied()` judges one verdict block against one manifest array (`src/pi/session-path.ts:39-64`, `src/pi/extension.ts:875-897`, `src/supervisor/finalization.ts:96-121`). A shared batch config cannot satisfy the current gate.
- **F15 — The trusted attester is enforced; the different-family verifier is not.** `session.attester` must exist and match an agent, and `FinalizeGate` ignores any other agent's criteria (`src/contracts/session-schema.ts:106-108`, `src/contracts/session-schema.ts:173-179`, `src/runtime/finalize-gate.ts:71-90`). By contrast, "different model family" exists only in the triage verifier design text (`docs/explorations/triage-automation/triage-verifier.md:74-82`); code has no family concept.
- **F16 — Completed artifacts are treated as frozen, but only partially enforced in code.** The runtime writes one `final.md` and one unedited `findings.md` into `run-details`; `SessionState.complete()` is only reachable from `FINALIZING`; session shutdown skips aborting a COMPLETE run to avoid overwriting `final.md` (`src/artifacts/final-writer.ts:18-38`, `src/control/session-state.ts:26-38`, `src/pi/extension.ts:310-315`). There is no filesystem immutability, so a batch design must preserve the policy deliberately.
- **F17 — Per-run cost/stop bounds are real gates.** The schema requires per-run budgets and stop thresholds; `BudgetEnforcer` trips on agent cost, agent tokens, or global peer cost; the runtime stops the agent now or at a work-order boundary, or stops all peers on the global ceiling (`src/contracts/session-schema.ts:55-93`, `src/budget/budget-enforcer.ts:20-56`, `src/runtime/runtime.ts:1129-1149`). Batch automation needs an extra batch budget above this, not a weaker replacement.
- **F18 — Success is more than DoD match.** Even with a matching verdict block, the gate can still fail on stale citations, failed validation, or missing `plan.md` (`src/supervisor/finalization.ts:124-160`, `src/runtime/finalize-gate.ts:103-186`, `src/validation/run-contract.ts:1-20`). An auto-executed ticket is not done until its ordinary run gate passes.

## 5. Decisions the user must make

- **Q1 — Batch shape:** pre-triage the whole ticket set, or triage/execute one-by-one? Throughput vs early feedback and lower wasted triage (`docs/explorations/triage-automation/triage-loop-brief.md:113-124`).
- **Q2 — Loop home:** external driver, new extension batch command, or new batch run type? Lowest implementation cost vs strongest in-repo enforcement (`docs/temp-handoffs/04-triage-run-type-handoff.md:77-84`).
- **Q3 — Tracker authority:** where does the accepted DoD/refusal live: issue body, comment, generated manifest only, or both? Human readability vs lossless history vs implementation complexity.
- **Q4 — Verifier arbitration:** on one mismatch, do you hard-refuse automation, queue human review, or allow a re-author/re-verify loop? Safety vs automation rate (`docs/explorations/triage-automation/triage-verifier.md:89-95`).
- **Q5 — Intake predicate:** which tickets are eligible for auto-generation at all? Maximum throughput vs risk of launching tickets that are not AFK-ready (`docs/explorations/triage-automation/triage-loop-brief.md:72-80`, `docs/explorations/triage-automation/triage-loop-brief.md:121-124`).
- **Q6 — Stop policy:** first refusal/failure, fixed ticket count, wall-clock, or spend ceiling? Predictable cost vs batch completeness (`src/budget/budget-enforcer.ts:20-56`, `src/runtime/runtime.ts:1129-1149`).
- **Q7 — Model policy:** how is "different family" represented and checked automatically? Manual operator choice vs new schema/catalog work (`docs/explorations/triage-automation/triage-verifier.md:74-82`, `src/contracts/session-schema.ts:11-24`).
- **Q8 — Batch artifacts:** do you want a batch summary artifact in addition to frozen per-ticket run artifacts? One place to read vs another artifact format to maintain.

## What this research did not verify

- The live state, bodies, labels, or comments of GitHub issues `#163-#170`; the current repo tree has no tracker snapshot, and this document stays grounded in HEAD-on-disk evidence.
- A live end-to-end triage + verifier + execution cycle; the analysis relies on the recorded exploration artifacts plus current code, not a new run.
- Any code path for tracker writeback, because no such path exists at HEAD (`src/pi/extension.ts:415-651`, `src/pi/supervisor-prompt.md:10-24`).
