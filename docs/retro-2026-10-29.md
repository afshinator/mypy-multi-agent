# Retrospective — coding-agent environment, 2026-10-29

Scope. Suggestions for improving the _environment_ this agent works in, not for correcting any one change. Source: one session in `afshinator/mypy-multi-agent`, log at `~/.pi/agent/sessions/--Users-afshin-Documents-dev-multi-agent--/2026-10-29T00-29-09-914Z_01a1850f-8799-70ae-b16d-5f8232101980.jsonl` (5.3 MB, 1,539 records, 704 tool calls, 2,576,786 bytes of tool results), ending at HEAD `e0c0c56`.

Every figure below was measured by parsing that log, not estimated. The commands are at the end so a reader can re-run them.

**Nothing here is actioned.** These are candidates; each needs a ticket before work starts.

## S1 — The repo has no guardrail at all

`package.json` defines `lint` (biome), `typecheck` (tsc) and `test` (vitest). Nothing runs them: no `.github/workflows`, no active git hooks, and no aggregate `check` script.

Evidence that this bites: the session made 89 `edit` calls and 15 `write` calls, and three real failures were caught only because the agent remembered to run the checks by hand.
- a biome format failure that would have made `lint` exit 1 (`src/peer/peer-harness.ts`);
- an unused `result` binding that moved lint from 86 to 87 warnings;
- a TypeScript error, `Property 'attempts' does not exist on type 'SessionResult'`.

**Recommendation:** one workflow running `bun run lint && bun run typecheck && bun test` on push to `main` and on pull requests. About 15 lines. This is the only item that protects future sessions regardless of agent behaviour; an un-linted repo is a standing missed opportunity, not a neutral default.

## S2 — Subagent tooling is 36% of all tool-result bytes

| tool              | calls | bytes   | share | average    |
| ----------------- | ----- | ------- | ----- | ---------- |
| `bash`            | 555   | 977,566 | 37.9% | 1,761      |
| `edit`            | 89    | 414,549 | 16.1% | 4,657      |
| `subagent_status` | 12    | 366,045 | 14.2% | **30,503** |
| `subagent_result` | 5     | 348,171 | 13.5% | **69,634** |
| `await_subagent`  | 3     | 222,990 | 8.6%  | **74,330** |
| `read`            | 20    | 205,755 | 8.0%  | 10,287     |

The three subagent tools together: 20 calls, 937,206 bytes, 36.3%. Two compounded causes.
1. A completion notice arrives truncated, so the full payload is fetched again with `subagent_result`. Five of those average 69.6 KB.
2. `subagent_status`, used as a progress poll, returns about 30 KB per call. Twelve calls cost 366 KB.

**Correction (2026-10-30).** The byte figures above count the whole tool-result message.
A provider converts only `content` into a turn — the `details` field is never sent
(`convertToolResult`: `content: convertContentBlocks(content)`) — so they overstate what the
model reads. `subagent_status` is the clearest case: 30,503 B per call above, of which the
model receives **1,410 B**; the rest is `details: { run: cloneRun(run) }`. Measured on this log
as it stands now (it has grown since this retro was written), per tool, in content bytes:
the three subagent tools carry 150,068 of 1,999,772 content bytes (**7.5%**), against 937,206
of 4,027,372 full bytes (23.3%). `edit` shows the same inflation: 800,707 full, 22,438 content.

So **cause 2 is not a byte problem** — `subagent_status` costs 0.8% of content bytes (12 calls,
16,329 B) and its `details` is unread. **Cause 1 stands and is the real one**: `subagent_result`
is 5 calls and 74,239 content bytes, `await_subagent` 3 calls and 59,500, because a truncated
completion notice makes the payload be read twice. The recommendation's first part holds in
content terms too (a report path beats a report body); its second part now applies to
`subagent_result` only.

**Recommendation, two parts.** In the prompt of any read-only investigator: _write your report to a file and return only its path plus at most ten lines of summary_. The one writer agent that did this cost a fraction of the investigators that did not. Separately, reserve `subagent_result` for when a truncated notice is genuinely insufficient, and do not use `subagent_status` as a progress poll.

## S3 — `AGENTS.md` states something false and misdirects navigation

Line 42 says: "Single-context: root `GLOSSARY.md` + `docs/adr/` (the directory exists, **no ADRs recorded yet**)."

That is false. `docs/adr/0001-shared-parse-and-trace-format.md` exists, and `0002-peer-to-peer-prompts-deferred.md` was added in this session. An agent that believes the line never opens the ADR directory, which is where the reasoning behind non-obvious choices now lives — a navigation pointer that actively misdirects.

**Recommendation:** correct the line and point at `docs/adr/README.md`, then add the mechanical guard the repo already uses elsewhere: a test that every `docs/adr/*.md` appears in `docs/adr/README.md`, and that the "next: `NNNN-`" hint matches. Same shape as the template-listing guard in `test/integration/guardrails.test.ts`, which would have caught this drift.

## S4 — 94% of bash calls carried a redundant `cd`

526 of 555 bash commands began `cd /Users/afshin/Documents/dev/multi-agent && ` although the shell already starts in the repo root. About 26 KB of noise, and a scanability cost on nearly every call.

**Recommendation:** one line in `AGENTS.md` — the shell starts in the repo root — or drop the prefix. Mechanical, zero risk.

## S5 — 19 scratch scripts written into the repo root

`v.tmp.ts` 15 times, `p.tmp.ts` and `c.tmp.ts` 4 each, and 16 other one-offs; 46 write commands in total. Each costs create, run, and delete.

No scratch file reached a commit: `git log --all --name-only` is clean of `.tmp.ts`. That held only because each commit staged named paths; the single `git add -A` in the session happened to run on a tree that carried none.

**Recommendation:** a gitignored `.scratch/` directory named in `AGENTS.md`, or a `just scratch` recipe; and prefer `bun -e` for a snippet short enough to inline.

## S6 — Three failed calls from platform assumptions

- `timeout` — not present on macOS.
- `cat -A` — BSD `cat` does not take it.
- `python3 -c "import yaml"` — `yaml` is not installed for the system Python, although the repo's own bun has it as a dependency.

One more class of the same kind: `rg -rn` was written meaning "line numbers", but `-r` means replace, so two commands returned garbled output before the mistake was noticed.

**Recommendation:** one line — macOS/BSD userland, bun is the script runner and has `yaml`, `rg -r` is replace.

## Negative results

- **No no-op steering rules found.** The first hypothesis — that the global `AGENTS.md` reference-code rule (D1..Dn, O1..On) is ignored — measured "169 assistant messages contain a code". That regex also matches unrelated repo strings such as `RT-8 D1`, so the measurement is contaminated and the claim is unverified. The retro's own metric fell into the same trap as the session it audits: a number was taken before its definition was pinned.
- The steering rules that mattered were obeyed and should stay: "a finished task run is frozen", and the answer-only reading of review verbs.
- The 555 small verification commands are not waste. They are what caught the recurring count errors (a wrong "9 of 11" rounds, a wrong 34-versus-35 config count, three wrong line ranges, three case-sensitivity slips). That habit should be preserved even at this token cost.
