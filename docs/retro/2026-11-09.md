# Retrospective: 2026-11-08 session (batch ladder rungs 3–4)

Session source: `2026-11-06T22-05-14-923Z_01a1b2e5-012a-71fe-803c-0279470fe582.jsonl`
(2026-11-06T22:05Z → 2026-11-08T21:16Z). 113 user turns, 923 tool calls: bash 811, edit 52,
read 39, write 15, subagent 1. 53 calls failed or returned errors. Total time spent inside
tool calls: 16,585 s (4.6 h), of which 3,751 s was `sleep` waiting and ~4,800 s was
`mypi-batch prepare`.

## F1 — High: the write guard refuses writes on turns it classifies as ambiguous

`scripts/write-guard.ts` derives one of `action` / `answer` / `ambiguous` from the last input
event's opening words, and refuses every write unless the mode is `action`. Two live defects:
- **A user-invoked skill prompt is always `ambiguous`.** The input text starts with
  `<skill name="…">`, so none of the `^`-anchored patterns (`WRITE_ACTION`, `QUESTION_START`,
  `READ_ACTION`) can match; `writeMode` returns `ambiguous` and the guard blocks the write the
  skill itself mandates. Reproduced in this retro session: `/skill:retro` mandates
  `docs/retro/<date>.md` and `write` was refused with "Write blocked without an explicit
  instruction". Not the same cause, and already fixed, was the supervisor block at
  `2026-11-07T01:35Z` ("Every write channel is blocked"): the guard in place then required a
  `ui.confirm`, which an unattended peer does not have — that is #415's `MYPY_UNATTENDED` path,
  not the classifier.
- **A bare `go ahead` was `ambiguous`, and `verify X, then go ahead` was `answer`.**
  `WRITE_ACTION` only accepts `go ahead` when a write verb follows it, and `COMPOUND_WRITE` only
  scans after `and`/`then` for a write verb. Both forms are how this session authorises work, so
  the turn that asked for the fix was refused as answer-only.
- **`\b(patch|unzip)\b` matches a path, not a command.** Any command naming a `.patch` file is
  classified as a write, so read-only inspection is blocked: `ls -la .diff403.patch`,
  `cat x.patch`, and even `rg -n patch docs/` all returned `true`. The test table had no
  `patch` case at all (`test/scripts/write-guard.test.ts:34-53`), not a command-only one.

Fixed as: `patch`/`unzip` moved to `HEAD_WRITES` and matched against the segment head; a
leading `<skill` classified `action`; `AUTHORISE` (`go ahead` / `do it` / `proceed`) matched
anywhere but after the `?` check, so "should I go ahead?" stays a question. Ticket: #452.

## F2 — High: no blocking status surface for a batch run the agent did not start

When the run is started from a terminal, the agent's only window is `run.log`, so it polled
with `sleep`: 22 calls, 3,751 s (1.0 h) of dead wall time, the worst being `sleep 480`,
`sleep 420`, `sleep 420`, `sleep 420`, `sleep 400`. The same absence hides progress during
`mypi-batch prepare` (932 s, 884 s, 558 s in this session), which reads as a hang: the user's
report was "I started it and i see no output at all".

`mypi-batch` has `new | prepare | run | launch` (`src/batch/cli.ts:250`) and `run` blocks, so
nothing covers "someone else's run, tell me when it is done". Add `mypi-batch status <slug>
[--wait]`: print each ticket's state from `run-details/`, block until `final.md` exists or the
run is dead, exit with the outcome. That replaces blind sleeps with one call and gives the
human a progress line. Ticket: #453.

## F3 — Medium: the code-review skill spawns reviewers without bash

Both reviewers were dispatched read-only and each stopped to ask the parent mid-run: "I have no
bash tool in this subagent (only read/grep/find/ls), so I cannot run `git diff`". The parent
answered both, wrote a 395-line diff to `.diff403.patch` in the repo root, and re-steered.

`.agents/skills/code-review/SKILL.md` tells the parent to put "the full diff command" in the
reviewer brief but never says the reviewer needs a shell, and it also asks the reviewer to "run
`bun run check`" — a 25 s suite that the parent has already run and CI will run again.

Fix the skill: reviewers get `bash` (read-only, no `write`), the parent dumps the diff once to a
scratch path and hands the path, and the reviewer brief drops the check run. Ticket: #454.

## F4 — Low: the `cd` prefix rule is a no-op

`~/.pi/agent/AGENTS.md` (line: "The shell already starts in the working directory you were
given, so a command needs no cd prefix (#126)") was in place before the session started
(mtime 2026-11-06 14:07, session start 22:05). 764 of 811 bash calls nevertheless began
`cd /Users/afshin/Documents/dev/multi-agent && `. The line pays context on every turn and
changes nothing. Either delete it, or strip a leading `cd <session cwd> && ` in a `tool_call`
hook next to the write guard — ~60 chars per call, ~12k tokens over this one session.

## F5 — Low: the read-via-shell rule is a no-op

The same file says "Use read to examine files instead of cat or sed". The session made 162
`sed -n` calls, 68 `grep -n`, 19 `rg -n`, and 39 `read`. Slicing by line range is what the work
needed, and nothing broke, so the line changes nothing. Prune it; keep only the mechanics that
do bite (heredoc hangs, `@-`, BSD tools).

## Verified fixed during the session (no action)

- Branch start point (`git switch -c <name> origin/main`) is now a written rule, and the

## Guardrail status

The repo has the guardrail the retro looks for: `.github/workflows/check.yml` runs
`bun run check` (biome, oxlint, both typechecks, both suites) on every PR and on main, and
`.githooks/{pre-commit,pre-push}` refuse the two unrecoverable mistakes cheaply. The lint
failures in this session (`error: script "lint" exited with code 1`, 10 occurrences) were
caught by that gate, as designed. No new guardrail is needed; the gap is F1's missing test
class, which belongs in the existing `test/scripts/write-guard.test.ts`.

## Tickets, in the order to do them

1. **#452 — `priority:high`** (F1). A harness that refuses a mandated write is a correctness
   failure, not a cost: it stopped a supervisor mid-ticket and blocks every skill that writes.
   **Fixed in this session** (`scripts/write-guard.ts`, 43 cases in the existing suite).
2. **#453 — `priority:normal`** (F2). 1.0 h of dead wall time in one session, and a 15-minute
   `prepare` that reads as a hang. Real cost, no incorrect outcome, so below #452.
3. **#454 — `priority:normal`** (F3). Every review loses two steer round trips and the parent
   has to hand over a dumped diff; a reviewer without a shell cannot read the diff at all, so
   the skill is broken rather than merely untidy.
4. **#455 — `priority:low`** (F4 + F5). Two no-op lines in `~/.pi/agent/AGENTS.md`, one of them
   fixable mechanically; nothing is wrong once you know the model ignores them.

F4 and F5 share one ticket because both are one-line edits to the same file. No
`ready-for-agent` label on any of them: that is the triage step's call, not this retro's.

# Retrospective: the 2026-11-09 batch-automation session

Session: `2026-11-09T21-04-48-083Z_01a1c220-bdd2-719f-8801-5fae09a92589` (21:04Z → 2026-11-10T02:18Z).
87 user turns, 676 tool calls: bash 633, edit 32, read 9, write 2.

Fifteen tickets landed (#427, #455, #460–#466, #469, #478, #483, #484, #487, #489), plus the findings
reconciliation, the ADR amendment and the batch guide's record layout. The code defect count was low.
The friction count was not, and most of it came from this machine.

## F5 — High: the write guard refused 35 writes, 21 of them writes the user had already ordered

Measured: 35 tool results in the transcript contain `Write blocked`. Grouped:
- **14** `Write blocked without an explicit instruction`, on `gh issue comment`, `gh issue create`,
  `gh issue edit` and heredocs writing to `/tmp`. Every one was a step the user had asked for in the
  same turn ("file it", "post it", "triage 489"). The classifier reads the last user message for an
  action verb and does not treat a triage invocation, or an approved plan, as an instruction. Cost:
  nine extra user turns of a single word, and the same work re-issued.
- **7** `state the reconcile line before the first write`, a prose contract the guard demands before
  the first write of a turn. Nothing in context said so up front, so the contract was learned from
  the refusal, seven times.
- **2** `blocked on a request that asked for an answer` — "verify the details of 478, then when clear
  tackle it" read as answer-only.
- **2** `HEAD is main, so there is no branch to land on` — the guard working correctly.

Several refusals reached the agent as `(empty command)` with no text, so the reason was invisible and
the correction was a guess. The same class fired while writing this retro.

## F6 — High: the guard does not stop a repository write while `HEAD` is `main`

The rule is in `AGENTS.md` ("Create a branch with an explicit start point"), and it is enforced only at
commit time, by the pre-commit hook and `just land`. Twice this session files were edited with `main`
checked out, both by `python3 - <<'PY'`, which the guard does not classify as a write. One commit was
refused by the hook; the other was moved onto a branch after the fact. The write is the mechanical
violation, and the guard is the only component placed to see it before the edit.

## F7 — Medium: the no-sandbox branch was untestable where it was written

`bun run check` was green locally and the PR check failed on Linux. The sandbox suite created fixtures
under `/Users/Shared` in a `beforeEach` that also ran for the always-executed "says why it is skipped"
test, so the Linux-only path threw instead of skipping. That path had no local exercise because
`sandboxAvailable()` reads the filesystem and cannot be forced: the one code path CI always takes was
the one the author could never run.

## F8 — Medium: the record-file authority drifted from the writer, and its guard asserted the stale list

`PREPARE_RECORD_FILES` is what `test/integration/guardrails.test.ts` checks the guide against. It was
written when evidence lived in `tickets/<n>/`, so after #460 moved it into `tickets/<n>/attempts/<k>/`
the guard passed on three files by accident — their old paths still appear in the guide's `.gitignore`
sentence — and failed on the rest. A guard that pins a hand-written constant cannot notice that the
constant is the stale thing. Fixed in `081216c`; the mechanism that allowed it is unchanged.

## F9 — Low, no change recommended: `just land` prints the main run without waiting

Each landing ended with `main check (not waited on)`, whose comment claims the merge tree is the one
the PR check passed. True only when `main` has not moved: a rebase merge onto a newer `main` tests a
tree the PR never saw. The agent verified the last runs by hand. Worth a sentence in the comment, not a
ticket.

## Not findings

- `AGENTS.md` is 75 lines and `CODING_STANDARDS.md` 67: no context-load problem, no disclosure needed.
- Shell mechanics all fired correctly (`sed -i ''`, no `timeout` binary, `rg` without `-r`, `gh` node
  ids vs REST ids for comments).
- 178 `sed -n`/`grep -n` calls against 9 `read` calls is not a regression: line-range reads were what
  the work needed, which is why #455 deleted the rule that banned them.

## What worked, worth keeping

- **Measure before designing.** Every security decision was grounded in a run: the `sandbox-exec`
  profile table, `git commit` failing on `index.lock`, `commandSafetyFaults` accepting
  `rm -rf ~/Documents`. Two of those measurements overturned the mechanism the ticket itself proposed.
- **A guard over a hand-written constant** is better than none: it caught three-file drift even while
  two of its own expectations were wrong.
- **A proof in the ticket body** made triage cheap: #483, #484, #487 and #489 each carried a
  reproduction, and triage only had to re-run it.
